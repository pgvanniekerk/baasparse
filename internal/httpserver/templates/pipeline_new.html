Input format

Each record's fields are the element's attributes plus its child elements' text, e.g. <cdr><msisdn>278…</msisdn><seconds>90</seconds></cdr>.

Streaming — memory stays bounded no matter the archive size. One archive = one processed-file record; a bad member quarantines the whole archive with the member named in the reason.

Declared input fields

These fields define the input structure — for DSV they are the columns in order, for JSON the object keys — and each value is interpreted as the type you choose. They are also the dropdown choices when you map the output. Add them by hand, or click “Parse from sample” to read the DSV header row / JSON keys from the sample on the right.

Destinations

Each destination defines its own output — which fields it carries, in what format, and where it lands. Billing can take three billable columns as pipe-delimited DSV while revenue assurance takes every field as gzipped NDJSON. The input is decoded once and shaped per destination. Destinations deliver independently: if one is down, the others still get their data and the failed one retries on its own.

Consolidation

Ten 100-record files become one 1000-record file. Records are preserved exactly; only the file boundary changes — this is what downstream billing systems expect instead of a spray of tiny files.

Max wait is how long a partial group is held back before it is written anyway. With no wait set, nothing is written until a full batch has arrived — so set it unless your input always arrives in complete groups.

These limits are pipeline-wide, not per destination: a batch is one frozen set of input files, and every destination receives that same set. That is what makes delivery exactly-once — if two destinations grouped files differently, the overlapping files would be delivered twice. Compression is per destination (it is a property of how that destination receives the object), and lives in each destination's Delivery section.
